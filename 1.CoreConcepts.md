## Core Concepts

These are just general concepts to keep in mind and think about when writing a container module. 

### 1. Container Immutability

**Key concept:** Modules should be treated as immutable, ready to be shutdown
- **Statelessness:** Design your application to be stateless. E.g. a function should always return the same output given the same input, no `self.att` attributes. A pod running your container might and will die out of nowhere and be restarted, it can and will be run several times at once in different instances, each of these when given the same data must return the same values.
- **Recreatable:** Any container should be able to be destroyed and recreated without data loss.
- **Configuration externalization:** Never hardcode configuration in your container images. Openshift has YAML (Get to know here: https://www.redhat.com/en/blog/yaml-explained-for-rosa-users) files that are used for configuration, so whatever would be in config or .env in our previous apps should be in YAML files, more on that in later section.

### 2. Decoupling

**Key concept:** Each container should only know of itself, and MUST NOT be aware of the inner workings of other modules.
- **Kafka communication:** All I/O to and from OQ will be done via Kafka. There is no communication with outside objects that is not done via kafka topics. There is no database and no file system.
- **Interface clarity:** In the context of decoupling, you should think of your application as two parts
	- the API  -> In our context this is AVRO formatted data in a pre-specified format received through a Kafka Consumer
	- The inner app -> This is where everything else should be, generally all logic, processing, etc should be implemented here. The API should just be callbacks to functions from the inner app, what can be changed here should be changed here. The inner app does not know of the API. 

### 3. Resource Awareness

**Key concept:** Containers operate with limited resources (afaik 16gb ram) for the time being there is no known data that should have the need to be processed in parallel, or batched due to memory constraints. In my opinion this being the case we shouldn't think about distribution of data processing across pods (using pyspark or other libraries) until the requirements change. But this is something we should probably talk about together.

### 4. Health Management

**Key concept:** Applications must communicate their health to the platform.

- **Self-monitoring:** Each module should have health-check api for openshift to probe. (e.g. is service running). This will be stated more precisely after analysis done by JS a BS.
- **Fast failure detection:** Fail quickly and clearly when unrecoverable issues occur.
- **Retrying failed data:** We will use Kafka DLQ's (Dead-Letter Queues) for retrying data that has failed due to external reasons (send API being down, Resource constraints, configuration errors...)
### 5. Kafka Communication

**Key concept:** Use async Kafka API for i/o, will be specified and some baseline to work with will be delivered by DB
- **Kafka serialization format:** AVRO

### 6. Observable Applications

**Key concept:** Applications should expose their internal state for monitoring.

- **Structured logging:** log in structured formats (json) to standard output.
- **Metrics exposure:** Provide meaningful application metrics via standard endpoints.

### 7. Configuration Management

**Key concept:** Configuration should be separated from code and injected at runtime.

- **Environment variables:** Use environment variables for configuration. (in YAML)
- **Configuration hierarchies:** Implement sensible defaults with override capabilities.
- **Runtime reconfiguration:** Support configuration changes without redeployment when possible.

### 8. Continuous Delivery Readiness

**Key concept:** Applications should support automated deployment pipelines.

- **Automated testing:** Include comprehensive tests that can run in CI/CD pipelines.
- **Rollback support:** Design for safe rollbacks in case of deployment failures. (Separate git commits into v. small independent changes)
