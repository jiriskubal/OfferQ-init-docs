# Monitoring options

I would consider three different approaches, with the final decision being made once we reach OpenShift and have a clearer understanding of log functionality. This will influence the overall solution.

**Option 1: Elastic Stack (ELK)**
   If we need to use Logstash, as mentioned in the Confluence documentation, the best route is to choose the Elastic Stack (ELK), which consists of three technologies that integrate well with each other:

   - **Logstash**
     - Processes logs and parses JSON, adding metadata from OpenShift (e.g., pod_name).
     - Accepts data from multiple sources simultaneously, helping to gather, process, and transform logs and events.
     - Allows normalization and preparation of data before sending it to Elasticsearch.
     - Send logs to Elasticsearch.

   - **Elasticsearch**
     - Enables full-text search.
     - Indexes logs for faster search.

   - **Kibana**
     - Serves to visualize data.
     - Allows drag-and-drop schemas, although it seems somewhat outdated now.
     - Enables log tracking on the stream tab.
     - Offers various graph options and allows monitoring of individual metrics, though it’s not primarily designed for health-checking pods however, it is possible.

   **Overall**
   This solution seems fine, although it is somewhat outdated. The documentation is not entirely clear, but the OpenShift section that deals with ELK deployment helps with navigation. This approach is more focused on monitoring errors and success rates rather than health status (CPU, GPU, memory).

**Option 2: Grafana + Prometheus + Loki + Possibly OpenTelemetry**
   - **Loki (Grafana)**
     - Used for log collection. It has its own agents and must run as a service.
   
   - **Prometheus**
     - Primarily focused on monitoring pod health, functions, RAM, CPU, GPU, and process duration. It is possible to measure the speed of individual functions in code using decorators.
     - Business monitoring can also be implemented, but it’s more complex.
     - Implementation may occur in later stages of development.
   
   - **Grafana**
     - Currently one of the most modern frameworks for data visualization.
     - Easy integration with data from Loki/Prometheus.

   **Overall Opinion:**
   This is probably the most commonly used combination for monitoring microservices. All mentioned frameworks and technologies have excellent documentation. Grafana even provides video tutorials, which can be helpful. Unlike ELK, which lacks documentation, all these tools are open-source (Apache License v2.0) and can be used freely. While ELK also has an open-source license, it comes with certain conditions.

   Grafana and ELK are already running in the bank on other applications. For example, ADAM uses Grafana on AWS, but it's primarily for health monitoring.

## Monitoring OpenShift Pods
Monitoring clusters and pods should be accessible in the OpenShift frontend (e.g., Prometheus can connect to this data and display it elsewhere). We need to create a space for log storage (indexing) on OpenShift, likely in the form of a [persistent volume](https://docs.redhat.com/en/documentation/openshift_container_platform/4.8/html/storage/understanding-persistent-storage) (PV). All of this is well documented and includes deployment examples.

Elasticsearch as a pod will open a persistent storage where logs will be stored - a durable disk storage for container applications. Without persistent storage, all data would be lost upon pod restart.
